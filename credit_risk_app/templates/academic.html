Academic Interpretation

The reasoning behind every major methodology choice in this project, grounded in this project's own numbers rather than textbook generalities — the questions a viva or interview is likely to ask.

Why Is This a Classification Problem?

The business question — "will this account roll to 90+ DPD in the next 6 months?" — has a binary answer, so roll_to_90p_6m is a binary label and this is supervised binary classification, not regression (which would fit if predicting, say, the exact DPD value) or clustering (no labels would be used at all).

Why Time-Based Validation Is Required

Two properties of this data make a random train/test split actively misleading:

  • The target looks forward in time. A random split can place an account's March observation in training and its own April observation in test — the model would effectively see the future.
  • The data is panel data, not independent rows: the same trade_id appears in {{ "%.1f"|format(summary.row_count / summary.n_trades) }} monthly observations on average. Consecutive months of the same account are highly correlated, so random assignment leaks account identity across the split even without leaking the future directly.

This project's split: train on {{ "{:,}".format(models[0].metrics.train.n) if models else '' }} observations through 2024-11, validate through 2025-04, test out-of-time on 2025-05–2025-09 — see the OOT Split Simulator. A further {{ "{:,}".format(maturity.immature_rows) }} rows ({{ maturity.first_immature_month }} onward) are excluded entirely because their 6-month outcome window isn't complete yet — the Data Quality Dashboard flags this as a right-censoring issue, not ordinary missingness.

Why AUC Alone Is Insufficient

AUC summarizes ranking quality averaged across the entire score range — including the large middle of the population a collections team will never act on. The actual decision this model supports is narrower: "given capacity to contact only the riskiest 10-20% of accounts, how many genuine bads does that capture?" That is exactly what top-decile capture and KS measure and AUC does not directly answer. In this project, all four models happen to rank consistently on both AUC and top-decile capture, but that's not guaranteed in general — a model can have a higher AUC while being less useful for a fixed-capacity queue if its advantage comes from separating already-safe accounts in the middle of the distribution rather than sharpening the top of the ranking.

Why Gini, KS, and Top-Decile Capture Matter Here

  • Gini (= 2×AUC − 1) is the same ranking information as AUC, rescaled to the 0-1 convention credit risk teams use.
  • KS finds the single score threshold where good and bad accounts separate most — the natural place to set an operating cutoff.
  • Top-decile capture answers the direct operational question above and is the metric the Model Screening page actually recommends on.

Why Class Imbalance Matters

Only {{ summary.kpis.roll_90p_6m_rate }}% of observations are positive. A model optimizing plain accuracy could score {{ (100 - summary.kpis.roll_90p_6m_rate) | round(1) }}% just by predicting "no roll" for everyone — useless for this purpose. Every model here is trained with class_weight="balanced" (or scale_pos_weight for XGBoost) specifically so the rare positive class isn't drowned out, and evaluation leans on rank-based metrics (AUC/KS/decile capture) rather than accuracy, which stays uninformative under imbalance regardless of threshold.

Why Behavioral (Engineered) Features Matter

A single snapshot says what an account looks like now; it can't say whether that's an improvement or a slide. The Feature Engineering Lab's own signal-strength check makes this concrete: the strongest engineered features are all trailing-window aggregates — {% for n, c in top_rolling %}{{ n }} (r={{ "%+.3f"|format(c) }}){% if not loop.last %}, {% endif %}{% endfor %} — while single-month deltas are close to noise: {% for n, c in weakest_delta %}{{ n }} (r={{ "%+.3f"|format(c) }}){% if not loop.last %}, {% endif %}{% endfor %}. Accumulated behavior over a trailing window predicts serious delinquency far better than any one-step change, which is also why dpd_avg_3m and dpd_max_3m lead every feature importance ranking on the Explainability page.

Why Model Interpretability Matters

This project deliberately builds both an interpretable baseline (Logistic Regression, coefficients readable as odds ratios) and a higher-performing but less transparent challenger (XGBoost) — the champion/challenger pattern standard in credit risk. Interpretability isn't just an academic nicety here: a reviewer or regulator needs to see why an account was flagged, which is what the Explainability page's SHAP reason codes provide even for the black-box challenger. In this project the gap is small enough to make that trade-off real: Logistic Regression reaches {{ models[0].metrics.test.auc if models else '' }} OOT AUC against {{ models[-1].metrics.test.auc if models else '' }} for {{ models[-1].display_name if models else '' }} — close enough that interpretability is a legitimate reason to prefer the simpler model in a context where that matters more than the last few points of lift.
